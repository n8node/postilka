# План постепенного масштабирования Postilka

Целевые ориентиры (когда вырастет аудитория):

- ~500 одновременных пользователей в кабинете
- ~2000 постов в час
- ~2000 генераций изображений/видео в час

Сейчас пользователей нет — двигаемся **по шагам**, после каждого этапа смотрим мониторинг и только потом идём дальше.

---

## Шаг 1. Мониторинг нагрузки в админке ✅ (сделано)

**Что появилось:**

- Раздел **Admin → Мониторинг нагрузки**
- Снимки нагрузки раз в час (очередь постов, генерации, база, worker)
- Ежедневная сводка в Telegram с трендом и рекомендацией по оперативке

**Что настроить после деплоя:**

1. Admin → **Настройки → Telegram — уведомления**: бот, **ID личного чата**, включить уведомления
2. Admin → **Мониторинг нагрузки**: указать **сколько ГБ оперативки на сервере**, нажать «Отправить тест в Telegram»

**Критерий «можно жить спокойно»:** отчёты приходят, на дашборде видны цифры, worker «жив».

---

## Шаг 2. Настраиваемые лимиты без смены архитектуры ✅ (сделано)

**Цель:** убрать жёстко прошитые числа (3 поста / 30 сек / 10 соединений с базой), но **значения по умолчанию оставить как сейчас**.

**Что появилось:**

- Admin → **Мониторинг нагрузки → Нагрузка и очереди**
- Переменные окружения: `WORKER_PUBLISH_CONCURRENCY`, `WORKER_PUBLISH_INTERVAL_SEC`, `DATABASE_MAX_CONNS`
- Worker подхватывает concurrency и interval из админки без перезапуска
- Пул PostgreSQL — из env при старте backend/worker; в админке видно, нужен ли перезапуск
- Рекомендации по цифрам в зависимости от указанной RAM (6 / 16 / 32+ ГБ)

**Риск:** низкий, если дефолты не менять.

**Пауза:** 1–2 недели смотрим мониторинг.

---

## Шаг 3. Ускорение очереди постов (всё ещё один сервер) ✅ (сделано)

**Цель:** поднять потолок с ~360 до ~2000 постов/ч, не ломая UX.

**Что появилось:**

- Отдельный цикл публикаций в worker (интервал из настроек, по умолчанию 30 сек)
- «Опубликовать сейчас» — через очередь; UI ждёт завершения
- Для 32+ ГБ RAM в рекомендациях: concurrency 25–35, interval 5 сек

**Как включить высокую скорость:** в админке указать RAM → свериться с блоком «Рекомендуемые лимиты» → выставить значения → при смене пула базы перезапустить backend и worker.

**Риск:** средний при резком повышении лимитов без достаточной RAM.

**Пауза:** после выката проверить публикацию по расписанию и вручную; смотреть очередь в мониторинге.

## ⏸ СТОП-ЛИНИЯ

**Дальше не идём, пока владелец продукта явно не скажет «продолжаем».**

Шаги 4+ — только по команде.

---

## Шаг 4. Разделить фоновые процессы

- Отдельный процесс только для публикаций
- Отдельный — только для генераций KIE
- Сервер API не крутит генерации внутри себя

**Риск:** средний — нужно не забыть запустить все контейнеры.

---

## Шаг 5. Несколько копий сервера + посредник к базе (PgBouncer)

- 3–4 копии backend за nginx
- PgBouncer перед PostgreSQL
- Общий ограничитель запросов (Dragonfly), не в памяти одного процесса

**Риск:** средний — строка подключения к базе, деплой сложнее.

---

## Шаг 6. Защита от перегруза

- Лимит параллельных сценариев (workflow)
- Разные таймауты для «быстрых» и «долгих» API
- Потоковая загрузка в S3 при финализации генераций (меньше RAM)

---

## Шаг 7. Железо и контейнеры (DevOps, не админка)

- Лимиты памяти/CPU в docker-compose под 32 ГБ / 10 ядер
- Отдельные лимиты для PostgreSQL, backend, worker

**Важно:** «раздавать гигабайты ползунками в админке» не работает — это настройка сервера при деплое.

---

## Как принимать решение «докупать оперативку»

Смотрим **Мониторинг нагрузки** и ежедневный Telegram:

| Сигнал | Действие |
|--------|----------|
| Всё зелёное, тренд стабильный | Ничего не делаем |
| Очередь постов или генераций **растёт несколько дней подряд** | Готовим шаг 2–3, возможно +RAM |
| Telegram пишет «рекомендуем увеличить оперативку» | Планируем апгрейд до указанного объёма |
| Worker «нет сигнала» | Срочно: контейнер worker не работает |

## Связь шагов и метрик

| Метрика в мониторинге | Шаг, который помогает |
|----------------------|------------------------|
| Очередь публикаций | 2 → 3 → 4 |
| Генерации в работе | 4 → 6 |
| Соединения с базой (занято/макс) | 2 → 5 |
| Worker heartbeat | инфра / деплой |
